# 입력 검증 강화와 회귀 검사

2026-10-04 · Dot Motion Studio

이 문서는 기존 v5 기능 점검 이후 발견한 세 가지 입력 검증 문제의 수정 내용과 한계를 기록합니다. **이 강화 소스는 사용자 승인 후 2026-10-04(UTC)에 기존 [공개 Site](https://dot-motion-studio.jakeshin.chatgpt.site)의 v6로 운영 배포되었으며, 배포 성공을 확인했습니다.** 공개 범위·로그인 보호·기존 MCP capability와 플러그인 식별자는 유지했습니다. 이후 인증된 MCP 연결과 세 도구의 실제 호출도 확인했습니다([라이브 MCP 검사](#live-mcp-check)). Site 웹 UI의 실제 사용자 로그인·업로드·브라우저 다운로드와 운영 메모리 한도는 계속 별도 확인이 필요합니다.

## 수정 내용

1. **명시적인 null과 생략을 구분합니다.** `fps`, `alphaThreshold`, 격자 수·간격, 정규화 크기·정렬·자르기, 이동량 등의 기본값은 `undefined`일 때만 적용합니다. `null`은 허용된 형식이 아니므로 거절합니다. 공개 스키마에서 발견한 30개 옵션·컨테이너 경로를 엔진, 웹 API 핸들러, MCP 핸들러에서 확인했습니다. 사각형 좌표·크기와 이미 거절되던 필드도 포함합니다.
2. **체크섬은 실제 zlib 스트림 경계에서 검증합니다.** IDAT 전체의 마지막 4바이트를 Adler32로 가정하던 코드를 제거했습니다. 잘못된 스트림 뒤에 정상 체크섬을 추가하는 경우도 거절합니다. 검증이 끝난 첫 스트림 뒤의 미사용 바이트는 [PNG §11.2.3](https://www.w3.org/TR/png-3/#11IDAT)에 따라 무시합니다.
3. **DEFLATE 저장 블록의 LEN/NLEN을 검증합니다.** 길이와 그 1의 보수가 일치하지 않는 입력을 거절합니다. 잘린 스트림·잘못된 허프만 구조·거리·헤더도 디코더에서 검사합니다. 근거는 [RFC1950](https://www.rfc-editor.org/rfc/rfc1950.html)과 [RFC1951](https://www.rfc-editor.org/rfc/rfc1951.html)입니다.

추가로 MCP의 `arguments:null`은 `-32602`로, HTTP API의 `null` 본문은 HTTP 400과 `{ "error": "Input must be an object." }`로 반환합니다. 인증·권한·도구 발견·정상 출력 형식은 변경하지 않았습니다. 잘못된 중첩 옵션은 기존 MCP 도구 오류 형식인 HTTP 200, `result.isError:true`를 유지합니다.

## 디코더 선택과 크기 제한

PNG 입력 압축 해제만 정확한 버전으로 고정한 **pako 3.0.2**로 변경했습니다. 문서화된 `Inflate`, `push`, `onData`, `ended`, `err`, `windowBits`, `chunkSize`만 사용합니다. 별도 DEFLATE 파서를 작성하거나 비공개 라이브러리 필드를 읽지 않습니다. PNG·ZIP 출력 압축기는 기존 fflate를 유지합니다.

- 기존 입력 바이트·픽셀·프레임·합산 출력 픽셀·내보내기 제한 유지
- zlib 헤더의 압축 방식·윈도 크기·검사 비트 확인, 사전 사전(dictionary)과 gzip 거절
- 압축 입력을 **최대 1,024바이트**씩 공급
- 출력 묶음을 **최대 min(16,384, IHDR 예상 바이트 + 1)**로 제한
- 예상 크기의 버퍼 하나에 복사하며, 초과 묶음은 복사하기 전에 오류로 중단
- 첫 스트림 종료·오류 없음·정확한 출력 길이를 모두 확인

독립적인 공개 콜백 계측에서 8MiB까지 펼쳐질 수 있는 입력이 1×1 그레이스케일 IHDR로 위장한 경우 **출력 3바이트에서**, 더 큰 IHDR 경우 **49,152바이트에서** 중단했습니다. 둘 다 첫 1KiB 입력 공급 안에서 중단되어 전체 폭증 데이터를 모은 뒤 거절하는 방식이 아님을 확인했습니다. 저장소 회귀 테스트는 같은 원리를 32MiB 잠재 출력에 대해서도 확인합니다.

정상 최대 픽셀 RGBA16 사례의 8,001,000 스캔라인 바이트도 16KiB 이하의 콜백으로 처리했습니다. 이 결과는 로컬의 제한된 테스트이며 실제 운영의 128MB 메모리 상한·동시 요청 수·지연 시간 보장이 아닙니다.

### 의존성 변경

- 공식 npm의 `pako@3.0.2`, 추가 런타임 의존성 없음
- 고정된 무결성 값은 `package-lock.json`에 기록
- 기존 개발 의존성 `pako@0.2.9`는 `unicode-trie` 아래로 이동했고 그 버전은 유지
- 그 밖의 의존성 버전은 변경하지 않음
- MIT 및 Zlib 고지는 [라이선스 파일](../../public/licenses/pako.txt)과 [THIRD_PARTY](../../THIRD_PARTY.md)에 보존
- 독립 엔진 번들의 gzip 측정 증가량은 8,379바이트였으며, 이는 전체 운영 앱 전송량 측정이 아님

참고: [Pako 공개 API](https://nodeca.github.io/pako/classes/Inflate.html), [고정 버전 소스](https://github.com/nodeca/pako/blob/3.0.2/src/inflate.ts)

## 재현

```bash
npm ci
npm test
npm run test:png
npm run typecheck

```

`test:worker`는 저장소에서 빌드한 Worker를 공식 Miniflare/workerd로 로컬 실행합니다. 가상의 테스트 사용자 식별자는 이 로컬 실행에만 사용합니다. 배포 주소를 입력받지 않으며, 운영 서버에 신뢰 헤더를 만들어 요청하는 테스트가 아닙니다.


## 호환성과 검증 한계

- **드문 동적 DEFLATE 헤더:** 사용되지 않는 예약 거리 코드가 포함된 HDIST=31/32 합성 사례는 이전 디코더가 받아들였지만 Pako·Node zlib·Python zlib·Pillow는 거절합니다. RFC1951이 기술한 거리 코드 수의 전체 범위와 참조 구현의 동작 차이가 있는 호환성 제한입니다. 정상 생성 코퍼스나 기존 258조건에는 이 패턴이 없었고 실제 사용자 파일의 빈도는 측정하지 않았습니다. 안전하지 않은 느슨한 디코더로 되돌리는 보완 경로는 두지 않았습니다. 이런 입력은 일반 이미지 편집기에서 정적 PNG로 다시 내보내는 방법이 필요할 수 있습니다.
- 모든 PNG·RFC 입력에 대한 완전한 적합성이나 보안 무결점 보증이 아닙니다. 기존 비인터레이스 PNG·색 형식·비트 깊이 지원 범위는 유지합니다.
- 로컬 테스트와 별도로 [라이브 MCP 검사](#live-mcp-check)에서 기존 플러그인의 인증 연결과 세 도구의 실제 호출을 확인했습니다. Site 웹 UI의 로그인·업로드·브라우저 다운로드 전체 흐름, Android 설치·업데이트는 아직 확인하지 않았습니다. 이전 플러그인 업데이트 오류의 근본 원인이나 모든 계정에 대한 해결은 확인하지 않았습니다.
- production 부하 테스트나 동시성·메모리 한도 검증은 수행하지 않았습니다. 출력 콜백의 조기 중단과 요청별 제한을 직접 확인한 범위만 보고합니다.
- 이 수정은 세 입력 검증 문제를 해결하기 위한 것이며, 코드 실행·데이터 노출·인증 우회가 가능했다는 보안 취약점 주장은 하지 않습니다.
